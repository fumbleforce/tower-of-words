# Code structure and reliability QC — 10 October 2026

Codex. Reviewed main `31ed6254008467b43818d4d6ecc86f4d8618a2b6`; the cited paths were unchanged at `5b501000f`. Scope: simulation persistence, save slots, story loading, place entry, dependency checks and `ARCHITECTURE.md`. This is a focused audit, not a project-wide certification.

## Findings

### P1: Quick save can report success while saving old progress

`game3d/js/sim.js`, `save`, catches storage failures without returning an outcome. `game3d/js/saves/actions.js`, `saveTo`, then reads the previous autosave and copies it into the selected slot.

An in-memory probe using the actual saving functions kept yen 100 in the autosave, changed live progress to yen 900, and refused only the new autosave write. Quick save returned `true` and contained yen 100. The player receives success for progress that was never saved.

Make snapshot creation and persistence outcomes explicit. A failed current-state write must prevent a successful stale slot copy. Test through `createSaving`, rather than only testing the slot store. Sent to the active save-files builder under [#422](https://github.com/fumbleforce/tower-of-words/issues/422), inbox X-1182.

### P2: A failed slot load can still replace Continue

`game3d/js/saves/store.js`, `adopt`, writes the slot payload into `SAVE` before writing `AUTO_META`. If metadata fails, it returns `false` although Continue now points at the chosen slot. `actions.js`, `loadInto`, interprets that result as failure and resumes the current game.

The probe began with office/yen 900 and selected train/yen 100. Refusing only `AUTO_META` made `adopt` return `false` while the autosave changed to train/yen 100.

Either treat a committed payload as success and repair missing metadata, or restore the previous payload before reporting failure. The result must describe the state actually persisted. Also assigned as an acceptance case for [#422](https://github.com/fumbleforce/tower-of-words/issues/422).

### P2: Missing story modules become successful empty stories

`game3d/js/runner.js`, `load`, catches import failures and supplies `{ nodes: {}, on: {} }`. A probe with a missing later-day module returned that empty object without a recovery error. In `game3d/js/places/lifecycle.js`, `enter` accepts it, leaves the previous place, clears the goal and saves the destination. The loader behavior was reproduced; the travel consequence was established by reading the entry path, without a browser failure injection.

Keep explicitly intended fallbacks, but distinguish them from failure to load registered story content. Failed entry should preserve the current place and progress and offer retry. Track the entry-boundary regression under [#426](https://github.com/fumbleforce/tower-of-words/issues/426).

## Structural assessment

The slot-store factory already accepts storage, thumbnail and clock dependencies. The save defects can be fixed within that boundary; they do not require an architectural rewrite. The broader coupling between simulation, UI and storage makes error handling harder to follow, but the demonstrated failures should be addressed before proposing a wider refactor.

The dependency checker covers unresolved imports and newly introduced cycles. It does not enforce inward architectural dependencies; `ARCHITECTURE.md` explicitly leaves that to review. No automated architectural guarantee is claimed here.

## Validation and follow-through

The reviewer ran 31 existing save/dependency tests successfully and three additional in-memory probes that exposed the failures above. No full application run or private-content inspection was part of this audit. Existing tests passing does not establish that failure paths work.

All three findings have implementation owners through work issues. None requires a product decision from Jørgen. Re-review should exercise storage refusal and missing-module entry at the public interfaces, including the state left behind after an error.
